# Deploying to Cloudflare (Workers + R2)

This project uses Workers with static assets through the OpenNext adapter.
Everything below runs from the `site/` folder. The portal's content, accounts and uploads live in an R2 bucket.

## One-time setup
1. `npx wrangler login`  (opens your browser; sign in to YOUR Cloudflare account)
2. `npx wrangler r2 bucket create dolly-portal`  (R2 must be enabled in the dashboard first; it asks for a card but the free tier is generous)
3. Secrets (each command asks you to paste the value):
   - `npx wrangler secret put PORTAL_PASSWORD`  (the first-time "admin" setup password)
   - `npx wrangler secret put PORTAL_SECRET`    (any long random string; signs sign-in cookies)
   - Optional, for emailed codes / password reset: `npx wrangler secret put RESEND_API_KEY` and `npx wrangler secret put MAIL_FROM`

## Deploy
`npm run deploy` performs the safe production workflow from one command:

1. Type-checks, lints and tests the project.
2. Builds and deploys the application Worker with the current Git commit as its version.
3. Refreshes `dollydesignstudio.pages.dev` with the same commit metadata.

The command stops before deployment when the Git workspace has uncommitted changes. This keeps GitHub, the Worker and Pages on the same version. It also selects the existing Dolly Design Studio Cloudflare account, avoiding Wrangler's multiple-account prompt.

`npm run deploy` and `npm run cf:deploy` are aliases for the same synchronized workflow. After both deployments, the command verifies that the Worker and Pages are serving the exact same Git commit; a mismatch is reported as a failed release.
Try it locally first (simulated R2): copy `.dev.vars.example` to `.dev.vars`, then `npm run cf:preview`.

## Custom domain
Cloudflare dashboard → Workers & Pages → dolly-design-studio → Settings → Domains & Routes → Add.

## Auto-deploy from GitHub (optional)
Dashboard → Workers & Pages → Create → Import a repository (your own GitHub account). Build command `npm run cf:build`,
deploy command `npx opennextjs-cloudflare deploy`. Add the same secrets under Settings → Variables and Secrets.

## Things to know
- Uploaded raster images use the configured `IMAGES` binding for cached, size- and quality-specific WebP variants. If resizing is unavailable, the original is streamed. SVGs keep their vector format. Image uploads are capped at 6 MB; video uploads at 50 MB.
- This application includes SMTP delivery for Node and a socket-based SMTP adapter for Workers. Preserve the configured studio mailbox; verify delivery in the target environment before relying on password-recovery email. Resend is also supported when configured.
- Sign-in attempt limits are per worker instance, not global.
- OTP redemption and attempt counters use conditional R2 writes, so simultaneous Worker requests cannot consume a code twice.
- Multipart image/font uploads enforce an actual streamed byte limit, including requests without `Content-Length`. Video uploads accept up to 50 × 1024 × 1024 bytes, validate the exact transferred size and share the one-at-a-time media gate. A video upload currently buffers up to 50 MiB; playback streams byte ranges instead of loading the whole video.
- Never commit `.env.local` or `.dev.vars`.

`pages-front/` is the optional Pages forwarding application, not unused build output.
`.open-next/` is generated by `npm run cf:build`; it can be recreated locally without deploying.
